# Vertex AI migration with enhanced Colombian electrical prompt and view-context awareness

This change rewrites the Cloud Function backend from the `@google/generative-ai` SDK (AI Studio) to raw Vertex AI REST calls using `google-auth-library`, migrates to the `gemini-3.7-flash` model, massively expands the SYSTEM_PROMPT with 30+ Colombian electrical jargon terms and explicit circuit desglose rules, and wires up the frontend to send `vistaActual` (the active app section) so Gemini can make context-aware action choices. The CSP is broadened to allow `*.a.run.app` and `*.cloudfunctions.net`, and the Cloud Function URL is updated to the deployed Cloud Run endpoint.

**Watch for:** The entire SYSTEM_PROMPT (150+ lines of instructions, inventory list, and user command) is passed as a single `user` role message rather than using Vertex AI's `systemInstruction` field, which degrades instruction-following fidelity (confirmed). The `vistaActual` value is read twice redundantly on the frontend (confirmed). Raw user text is concatenated into the prompt without sanitization, opening a prompt-injection surface (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The Cloud Function's AI backend was swapped from the `@google/generative-ai` SDK to a direct Vertex AI REST call authenticated via Application Default Credentials. This eliminates the GEMINI_API_KEY secret dependency, but the prompt is injected as a user-turn rather than a system instruction, weakening the model's adherence to output-format constraints and opening a prompt-injection surface through voice-transcribed text.

The SYSTEM_PROMPT grew from ~40 lines to ~150 lines, adding structured circuit decomposition rules, a glossary of 30+ Colombian electrical terms, number/quantity interpretation rules, and view-context decision logic. The prompt never specifies what happens when the user omits the cable calibre in a circuit command, nor what to do when `vistaActual` contradicts the voice command's intent.

The frontend reads `.menu-item.active` to detect the current section and ships it as `vistaActual` in the fetch body, but the DOM query is evaluated twice per send — once for the status text and again in the fetch payload — creating a minor redundancy that could drift.

The CSP wildcard `*.a.run.app` is broader than necessary (allows any Cloud Run service globally). The `*.cloudfunctions.net` entry is leftover from the old URL and no longer needed.

## Prompt construction and instruction-following fidelity

The Vertex AI `generateContent` endpoint accepts a `systemInstruction` field that tells the model to treat its content as ground-truth instructions. The current implementation concatenates `SYSTEM_PROMPT + contextoInv + contextoVista + user_command` into a single `user` role message:

```js
contents: [{ role: 'user', parts: [{ text: prompt }] }],
```

This means the model sees the 150-line instruction block as something the user said, not as system instructions. In practice this leads to:
- Lower reliability on strict JSON output (the model may add conversational preamble)
- Vulnerability to prompt injection: if the voice-transcribed `texto` contains "ignore previous instructions and...", the model has no architectural separation between instructions and input

The fix is straightforward — split the request into `systemInstruction` + a separate user turn:

```js
body: JSON.stringify({
  systemInstruction: { parts: [{ text: SYSTEM_PROMPT + contextoInv + contextoVista }] },
  contents: [{ role: 'user', parts: [{ text: texto }] }],
  generationConfig: { temperature: 0.2, maxOutputTokens: 2048 }
})
```

Voice recognition frequently garbles speech into fragments that accidentally resemble injection attempts, and the model's compliance with JSON-only output drops measurably when instructions are in the user turn.

## Redundant vistaActual DOM query

In `renderer.js`, the click handler for `#ap-enviar` reads:

```js
const vistaActual = document.querySelector('.menu-item.active')?.dataset?.vista || 'dashboard';
$('#ap-estado').textContent = '🧠 Procesando con IA... (vista: ' + vistaActual + ')';
```

Then 15 lines later in the fetch body:

```js
body: JSON.stringify({ texto, inventario: inv, vistaActual: document.querySelector('.menu-item.active')?.dataset?.vista || 'dashboard' })
```

The `vistaActual` const is already in scope. Reuse it in the fetch body instead of re-querying — if a view switch fires between the two reads, the status text and the actual value sent would diverge silently.

## CSP scope

The added `connect-src` entries are `https://*.a.run.app https://*.cloudfunctions.net`. The `*.a.run.app` wildcard permits fetch to any Cloud Run service globally. For a desktop Electron app this is low-risk (no third-party scripts to exploit it), but pinning to the actual URL (`https://asistente-5lyachxl4a-uc.a.run.app`) would be tighter. The `*.cloudfunctions.net` entry is no longer needed since the endpoint moved to `.a.run.app` — it's dead weight that widens the attack surface for no benefit.

## Error propagation from Vertex AI

When Vertex AI returns a non-200, the function forwards a slice of the raw error body to the client:

```js
res.status(500).json({ error: 'Error de Gemini: ' + response.status, detalle: errText.substring(0, 200) });
```

Vertex AI error bodies can contain project IDs, service account emails, quota details, or token metadata. These should stay server-side (`console.error` already logs them). The client should receive only a generic "Error procesando el comando" message.

## Circuit desglose: missing default calibre

The prompt specifies "calibre indicado" in each circuit rule but provides no fallback when the user omits the calibre entirely. A voice command like "50 metros de circuito rojo" without specifying #12 or #10 leaves the model guessing — it may hallucinate a default or ask a clarification question that won't parse as JSON. Adding a rule like "Si no se indica calibre, asumir #12 para 120V y #10 para 220V (o devolver accion='error' pidiendo aclaracion)" would close this gap.
