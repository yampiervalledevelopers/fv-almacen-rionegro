# Live voice agent — v2 review (post-fix pass)

Five of six v1 issues were addressed: "para" removed from stop-words with exact-match only, confidence >= 0.85 threshold gates direct execution, item dual-write eliminated (only `#o-add` click now), TTS polling fallback added, and `cerrarModal` resets agent state. The unauthenticated Cloud Function was correctly identified as pre-existing and skipped. The fixes are well-targeted.

Two new concerns emerge from the current code. First, `ejecutarDirectoIA` bypasses tool-tracking (`actualizarHerramientaDespacho`) and printing — the normal modal path does both after `registrarOrden`, creating a behavioral asymmetry for tool dispatches. Second, `confirmarModalPorVoz` announces success and resets state synchronously after clicking the save button, before the async handler finishes — if validation fails or the Firestore write errors, the user hears "Orden generada exitosamente" while the modal remains open and nothing was saved.

Watch for: tool dispatch tracking gap in direct execution (confirmed); premature success announcement in `confirmarModalPorVoz` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The direct execution path (`ejecutarDirectoIA`) writes the order to Firestore and updates stock, but skips two post-save steps that the formal modal handler performs: calling `actualizarHerramientaDespacho` for tools (which tracks who holds each tool) and triggering the print dialog. Any tool dispatched by voice will appear in the order but won't be reflected in the tool-tracking system, causing silent data drift in the herramientas dashboard.

The `confirmarModalPorVoz` function treats `btnGuardar.click()` as fire-and-forget: it immediately announces "Orden generada exitosamente" and resets `asistente.estadoAgente` to `libre`. Because the click triggers an async handler (validation + Firestore write + close modal), any failure in that chain is invisible to the voice agent — the user hears success, but the modal is still open with the error toast underneath the speech.

## Tool-tracking gap in direct execution

The formal modal save handler in `modalOrden` does this after `registrarOrden`:

```javascript
if (tipo === 'salida') {
  for (const it of items) {
    const mat = estado.materiales.find((x) => x.id === it.materialId);
    if (mat && mat.esHerramienta) {
      await actualizarHerramientaDespacho(it.materialId, responsablePrincipal, frente, 'salida');
    }
  }
}
```

`ejecutarDirectoIA` resolves items, validates stock, calls `registrarOrden`, builds a confirmation message, and returns. No herramienta loop. If a user says "despacha una pulidora a Pedro frente 5B" and the LLM returns it as a complete salida with confidence >= 0.85, the order is created and stock decremented, but `actualizarHerramientaDespacho` is never called. The tool tracking dashboard will show the tool as unassigned while the order says otherwise.

The fix is straightforward — add the same loop after `registrarOrden` in `ejecutarDirectoIA`:

```javascript
if (tipo === 'salida') {
  for (const it of items) {
    const mat = estado.materiales.find((m) => m.id === it.materialId);
    if (mat && mat.esHerramienta) {
      await actualizarHerramientaDespacho(it.materialId, responsablePrincipal, frenteVal, 'salida');
    }
  }
}
```

## Premature success announcement

`confirmarModalPorVoz` does:

```javascript
btnGuardar.click();                      // triggers async handler
asistente.estadoAgente = 'libre';        // immediate
asistente.modalTipo = null;              // immediate
return hablarAgente('Orden generada exitosamente.');  // immediate
```

The `#o-guardar` click handler is async — it validates items, checks stock, calls `registrarOrden` (network), then closes the modal on success or shows an error toast on failure. None of these outcomes are awaited by `confirmarModalPorVoz`.

Failure scenarios that produce a false success message:
- `estado.itemsOrden` has no valid items (voice-filled items not synced yet) → toast "Agrega al menos un material" appears, modal stays open.
- Stock insufficient → toast error, modal stays open.
- Firestore write failure → toast error, button re-enabled.

In all cases the user hears "Orden generada exitosamente" while looking at an error.

The cleanest fix is to refactor the save logic into a shared function that both the click handler and `confirmarModalPorVoz` can await, returning success/failure. Alternatively, `confirmarModalPorVoz` could observe modal close (which only happens on success) before announcing — but that's brittle.
